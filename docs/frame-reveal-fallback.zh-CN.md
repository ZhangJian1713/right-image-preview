# 解码完成后的帧等待阻塞

日期：2026-10-25。范围：DOM 主图就绪与交接；不改变解码策略、真实解码的 60 秒兜底、原图读取及宿主请求调度。

## 现象与证据

旧实现有两个独立的帧依赖：解码确认成功后仍 await 双 rAF 才发布就绪；首开整层可见性也等待 rAF 更新。若宿主暂停这些 JS 回调，即使 ImageBitmap 已成功创建、主图 complete 且布局有效，仍可能继续隐藏主图和显示加载中。普通浏览器下几十至几百毫秒的解码对照不能排除此类故障。

程序化最小复现让 rAF 不执行，解码 Promise 正常完成；旧版的两个回归用例失败，分别为未发布解码就绪、已加载图层仍隐藏。它证明控制流存在阻塞，不单独证明具体宿主暂停回调的原因。

## 修复

- 保留 `createImageBitmap` 优先、失败回退 `decode()`；不采用之前变慢的 decode-only 候选。
- 解码结束后正常等待两帧，同时启动独立 100ms 定时兜底。任一路完成即可通知交接；真实解码尚未结束时不启动此兜底。定时器是尽力调度，不能承诺后台页面在 100ms 内完成，更不代表物理呈现成功。
- 源切换、完成或最后订阅者取消时清理帧及相关定时器；过期访问不能揭开新图片，超时不记为成功解码缓存。
- 当前访问的主图 load 且布局有效后，整层可以显示；独立的渐进解码条件仍决定是否撤掉缩略占位，变换过渡继续等正常帧恢复。
- 长按浏览的已呈现确认保持原有语义，不因这个主图就绪兜底伪造已呈现时间。

## 本机浏览器复核

与前一轮沿用相同四种图片、生产构建方式和 Chrome 156.0.8078.47；1280×900，关闭邻图预热、人工缩略停留为 0。正常模式每种图片每个实现三次；停帧模式每种大 JPEG 每个实现一次，覆盖纯暂停 JS rAF 而定时器继续运行的情形，共 28 次。

正常模式下，原图 load 到组件 full-ready 的中位耗时（ms）：

| 图片 | 0.10.0 | 修复版 |
| --- | ---: | ---: |
| 渐进 JPEG，7008×4672 | 153.6 | 155.2 |
| 普通 JPEG，7008×4672 | 92.9 | 88.2 |
| PNG | 31.5 | 27.2 |
| 静态 WebP | 23.0 | 27.8 |

样本量有限，这些数值用于检查明显回退，不用于宣称普遍加速。首轮各组图片截图与 250ms 后截图一致，无页面错误；未逐帧录制，不能排除更早的短暂视觉异常。

停帧模式下，两张旧版图片在约 1.5 秒的观察窗口结束时，均已 complete 且 Bitmap 已完成，但图层 opacity=0、loader=on，未发布 full-ready。修复版两张图片分别约 310ms、214ms 完成逻辑就绪，图层 opacity=1、loader=off。时间包含本地加载和测量调度，不是精确首帧时间；没有用这个时间推断磁盘、网络或原宿主请求排队耗时。

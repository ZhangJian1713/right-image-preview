# 解码后固定帧等待的必要性调查

日期：2026-10-25。状态：未发布源码改动；已发布的 0.10.1 与 X Archive 安装版未因此改变。

## 结论与改动

未找到能够独立证明“解码结束后必须再等待两帧”的复现或收益证据。按本轮决策移除 `scheduleRevealAfterDecode` 中的两次 `requestAnimationFrame`，同时删除只为该等待服务的 100ms 定时器、帧句柄和清理分支。解码完成后立即通知订阅者。

保留 `createImageBitmap` 优先、失败后 `img.decode()` 的确认路径，真实解码的 60 秒尽力兜底、订阅共享、取消、换源校验和成功缓存；保留当前访问的布局条件、渐进缩略降级与 outgoing 旧图托底。`useStageReveal` 恢复变换过渡、长按展示节奏使用的帧回调不在本次移除范围内。

这项决定基于额外等待缺乏独立收益证据，并非证明所有平台都不可能出现显示问题。后续若有稳定复现，应针对实际缺失的布局或呈现条件修复，而不是直接恢复固定帧数。

## 三个不同问题

| 问题 | 当前依据 | 本轮处理 |
| --- | --- | --- |
| 是否读完并完成解码 | `createImageBitmap` / `decode()` 确认；此前仅改 `decode()` 的性能实验不能验证固定帧等待的必要性 | 保留 |
| 是否准备好 incoming 布局、保留 outgoing 到交接 | 当前 visit、加载通知、尺寸及布局 Effect；历史修复同时改变过多项条件 | 保留 |
| 解码之后再固定等两帧是否必要 | 没有隔离出其收益的历史证据；单变量对照观察到额外延迟，未观察到布局收益 | 移除默认等待及其独立计时兜底 |

`requestAnimationFrame` 回调处于渲染更新流程中，回调执行并不是合成器已经物理呈现的确认。HTML 对 `decode()` 描述了解码完成及保留解码数据至后续渲染更新的预期，没有规定组件必须再等待两帧。[渲染更新顺序](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering)、[图片 decode 定义](https://html.spec.whatwg.org/multipage/embedded-content.html#dom-img-decode)。这些规范不能替代具体 WebView 的像素验证。

## 历史来源

首次双帧等待见 [8677a2c，0.3.2](https://github.com/ZhangJian1713/right-image-preview/commit/8677a2ca6a41581d27664bde201b69fdb4b6a834)。该轮也引入 bitmap 确认并调整了图层、透明度、布局及保留方式；描述中的条带问题没有对应的单变量帧数实验。

后续 0.3.10—0.3.12 的黑屏一点记录，也同时涉及 outgoing 退为 1×1 和 incoming 全尺寸布局。旧文档中“必须重叠约两帧”的表述强于现有证据，已修正。当前成功缓存与 `preferFastReveal` 路径原本就能跳过这项等待，不能把旧描述理解成所有切图共同遵循的物理呈现屏障。

0.10.1 添加的 100ms 兜底解决了帧回调暂停时错误等待至解码期限的问题，见 [当时的验证](./frame-reveal-fallback.zh-CN.md)。它是固定帧等待的补偿机制；本轮移除等待后也不再需要。

## 实际 WKWebView 单变量对照

在实际安装的 X Archive / macOS arm64 WKWebView 中，使用同一官方 0.10.1 bundle，只临时代理该 helper 的两段精确帧回调。0 帧通过微任务执行链，1 帧在第一段原生帧回调内执行第二段，2 帧保持原生调用；其他 rAF、bitmap/decode、100ms 期限、探针和图层不变。代理已恢复，磁盘产物未修改。

同一张 3072×4096 JPEG、缓存已暖，按平衡顺序各测三次。每次都确认目标两段回调各匹配一次，避免误把快速路径当成实验。

| 模式 | 解码结束→DOM 就绪，三次（ms） | 中位数 |
| --- | --- | --- |
| 0 帧 | 4 / 6 / 3 | 4ms |
| 1 帧 | 4 / 4 / 4 | 4ms |
| 2 帧 | 37 / 21 / 20 | 21ms |

每次揭开后取四个 DOM 布局样本，36 个样本均为预期的 675×900 Fit，无 1px 几何或残留 outgoing。限制：只测一张暖缓存 JPEG；采样会增加原生帧回调；没有物理像素记录，不能据此断言没有一帧闪烁。

## Chrome 构建产物对照

环境：Chrome 156.0.8078.47，800×600，DPR 1。同一生产构建配置、同一套输入和响应节奏，仅改变解码后的 0 / 1 / 2 帧等待；保留 bitmap/decode、图层、探针等。三个隔离版本增加相同的 decode / reveal 诊断事件，记录实际执行帧数。另测没有这些库内诊断事件的最终候选构建；数据中的 variant `3` 是候选编号，**不代表等待三帧**。

输入包含同内容的 7008×4672 渐进 / 普通 JPEG，以及不同内容的 1033×1552 竖图。主图响应延迟 40ms 后以每 4ms 128KiB 发送；缩略图立即返回。冷路径关闭邻图槽位；暖路径使用 radius=1、slots=2、settle=0 并等待目标 display-ready。另覆盖无预置尺寸、缓存回访和快速切换。

首轮为 18 个计时会话、9 个采帧会话及 1 个校准会话。连续普通切图在 DOM 就绪后立即继续，后一张可能承担前一张尚未完成的绘制成本，端到端耗时随帧数并不单调；其中一个两帧冷竖图样本只执行一次回调便走了 100ms 兜底，不能把它归为完整两帧样本。完整记录保留在 JSON，未用于宣称普遍加速。

追加验证在普通动作后统一等待 250ms（不计入该动作耗时），快速切换仍请求间隔 8ms；24 个计时会话，每模式 / 路径三次。四种构建都通过相同的 Promise 包装记录实际当前主图 bitmap 完成，不新增解码调用。以下是冷路径中位数：

| 输入 | 两帧版：bitmap 完成→DOM 就绪 | 最终候选：同区间 | 两帧版：选中→DOM 就绪 | 最终候选：同区间 |
| --- | --- | --- | --- | --- |
| 渐进 JPEG | 10.5ms | 7.1ms | 277.5ms | 272.4ms |
| 普通 JPEG | 16.5ms | 13.3ms | 194.0ms | 187.0ms |
| 竖图 JPEG | 29.9ms | 10.1ms | 95.7ms | 73.4ms |

暖邻居与回访本来就多走快速路径，没有同样的移除收益；例如暖普通图选中→DOM 就绪中位数为两帧版 18.6ms、候选 20.0ms。小样本及调度噪声不支持承诺每张图都变快。所有会话无页面异常，最后均为当前原图就绪、可见且无 outgoing。

### 画面采集与有效性限制

用 CDP PNG screencast，`everyNthFrame=1`，收到即确认；画面顶部 8px 放入 rAF 序号、当前图和交接阶段标记。采帧与计时分开，避免把截图成本算进性能结论。[CDP Page 接口](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-startScreencast)。

比较原图就绪阶段与同输入的稳定参考像素，排除标记区域；RGB 平均绝对差大于 1，或最大通道差大于 16 的像素比例超过 0.5% 时标记异常。该阈值用于检测明显黑屏 / 条带，不能排除细线或小面积差异。

| 数据集 | 采集 surface 帧 | 原图阶段比较帧 | 超阈值异常 | rAF 标记序号缺口 |
| --- | --- | --- | --- | --- |
| 0 / 1 / 2 帧隔离对照，9 会话 | 806 | 494 | 0 | 114 |
| 最终候选，3 会话 | 497 | 395 | 0 | 31 |

额外校准注入四次单帧全黑及四次单帧左侧 16px 黑条，8/8 被检测到；校准本身仍有两个序号缺口。序号缺口可能包含漏采或没有独立合成 surface 的更新，CDP 不能据此保证覆盖每个物理呈现帧。部分快速切图动作没有独立识别出的 sharp 帧，包括候选暖路径的最后一次动作；最终 DOM 就绪检查通过，但这一段不能报告为像素验收通过。普通切换后的采样未检出明显异常，也不能据此保证首个物理呈现帧安全。

本地控制脚本位于临时 `/tmp/right-image-preview-frame-delay-study/`：`build.mjs` 生成隔离变体，`run.mjs` 驱动计时 / 采帧，`analyze.py` 比对像素；产物位于 gitignored 的 `.local-pack/frame-delay-study/`。隔离变体基于修改前的 0.10.1 helper，与候选分别构建；重建历史变体时还需使用该版本的 tuning 常量，不能混用本轮已删除常量的源码。脚本和 PNG 不进入发布包。

回归覆盖 bitmap/decode 完成后无需 rAF 或后置定时器、真实解码尚未结束不会提前揭开、取消订阅、共享解码、换源、超时不伪造成功缓存，以及渐进加载、旧帧托底、长按和邻图预热。2026-10-28 提交前复核补充了 bitmap 失败后等待 decode、两种解码 API 均失败时尽力展示且不缓存成功的测试；相关 11 个测试文件共 95 项通过，TypeScript、改动文件 ESLint、生产库构建通过。`size-limit` 实测 38.33 kB，低于 39 kB 限额。此次未重跑浏览器性能和采帧实验，上文保留 2026-10-25 的历史记录及其限制。

2026-10-28 核对 npm registry：`latest` 仍为 `0.10.1`，发布时间为 2026-10-25 16:09（Asia/Singapore），没有 `0.10.2`。下载 0.10.1 tarball 并验证 registry 声明的 SHA-512 integrity；包内 sourcemap 的 `imagePreviewDecode.ts` 与发布提交 `9973f3a5ce19b1b941b89fc29a2aedd038d07099` 完全一致，仍包含解码后的两帧等待和 100ms 兜底。因此 0.10.1 已发布的是此前停帧兜底修复，不包含本轮移除等待的改动。

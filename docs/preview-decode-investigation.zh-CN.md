# DOM 图片解码确认对照

日期：2026-10-24。结论：**本轮不将 `createImageBitmap(img)` 替换为仅 `img.decode()`，正式行为保持 0.10.0。** 候选已实现并验证，但在本机 Chromium 大 JPEG 上出现可重复的就绪耗时回退，不能作为已确认的性能优化交付。

## 背景与候选

0.3.2（`8677a2c`，2026-08-12）为切图时左侧／顶部条带闪烁引入位图确认；同次提交还改变了图层、透明度和揭开时序，不能单独据此证明 `createImageBitmap` 必不可少。该逻辑早于 WebGL 引入。

当前 DOM 路径先调用 `createImageBitmap(img)` 并立即 close，失败才回退 `img.decode()`；两帧后通知揭开。候选仅删除前一个分支，仍保留 `decode()`、两帧、60 秒超时、共享订阅、旧访问失效和旧帧交接，不修改对外 API。

Media Lens 分叉的 WebGL 路径使用 ImageBitmap 作为实际纹理上传输入；其 DOM 回退在 load 后报告就绪，且主要消费有界 Screen/Preview，不能据此认定本库直接显示大原图也可以立即揭开。

## 验证条件

- macOS、本机 Chrome 156.0.8078.47，无界面运行，1280×900 视口。
- 基线使用已发布 0.10.0 的生产构建；候选使用同一构建配置。两组共用 React 和测试宿主。
- 原图与 320px 缩略图由本机临时 HTTP 服务提供，不上传媒体；关闭邻图预热，将人工缩略停留设为 0，保留渐进显示。
- 四个样本：7008×4672 普通 JPEG、由同图生成的同尺寸渐进 JPEG、1460×1186 PNG、1033×1552 静态 WebP。
- 每个样本和实现运行三次，交替先后顺序；每次使用新的浏览器 context。计量从舞台原图 load 到组件 `full-ready`，该指标是逻辑就绪时间，不是屏幕首次显示的精确时间。
- 每组首轮对比首个可捕获画面与 250ms 后画面，隐藏控件以排除悬停／提示过渡。所有图片区域比对一致，无页面异常；这不是逐帧录像，不能排除更早的一帧闪烁。
- 初轮曾将生产基线与开发候选比较，已弃用该轮结论；下表仅使用相同生产构建方式的复核数据。

## 结果

单位 ms，三次中位数：

| 样本 | 原实现 load → full-ready | 仅 decode | 原实现首开总时长 | 仅 decode 首开总时长 |
| --- | ---: | ---: | ---: | ---: |
| 渐进 JPEG | 161.2 | 280.3 | 195.5 | 319.6 |
| 普通 JPEG | 86.9 | 174.2 | 120.5 | 207.4 |
| PNG | 27.2 | 29.0 | 60.6 | 63.0 |
| WebP | 24.1 | 37.7 | 56.0 | 73.7 |

原实现每次创建一次辅助 ImageBitmap，候选为零。减少位图创建没有在此次运行中带来显示加速；未测进程内存，不能声称减少了多少峰值内存。包装函数累计的 decode 时间可能含其他层及重叠调用，不用于归因。

候选的五个相关测试文件、56 项测试、TypeScript、定向 ESLint 和生产库构建通过，包括 Bitmap API 可用但永不返回时不依赖它、decode 失败／缺失、过期访问及交接保护。这只能说明状态逻辑通过，不能抵消浏览器实测回退。

原始聚合数据见 [JSON](./preview-decode-comparison-2026-10-24.json)，不含媒体路径或图片。临时宿主、两份构建与候选补丁留在 gitignored 的 `.local-pack/decode-check/`；运行脚本和测试媒体清单在 `/tmp/right-image-preview-decode-check/`，不属于发布包。

## 决策与验证边界

撤回候选的正式源码、测试及行为文档变更，保留本报告。没有发布、提交或推送新版本；60 秒兜底仍存在，也未复现等待到 60 秒的故障。

下一步需要在实际慢的宿主／浏览器上，使用能复现的原图，分别测量读取、load、Bitmap/decode 完成、两帧等待、占位停留及交接阶段，再决定优化哪个阶段。不能把 Chromium 结果推广到 Safari/WKWebView、Windows/Linux；本轮也没有确认历史条带问题现在仍存在或已消失。浏览器内部为什么使两条准备路径产生这个差异，仍待针对性 profiling，不能直接归因为重复完整解码。
